3. **Провайдеры.** Ни один провайдер не утверждён. В плане стоят рекомендации, а не одобрения (PROVIDER-01).
4. **Статусы проверок:**
   - **П** — подтверждено реальным вызовом конкретной функции;
   - **Ч** — частично: ответ получен, но данных или семантики не хватает;
   - **НП** — не проверялось;
   - **О** — отрицательный результат конкретного вызова. Это не доказательство, что весь сервис не работает.

   Исторический успешный вызов не гарантирует, что сервис доступен сейчас.
5. **Секреты.** В документе нет ключей, токенов и персональных данных.

## 2. Архитектура

Концепция v0.1 сохранена: аудит её предварительно одобрил.

### 2.1. Принципы

1. **Приоритет качества по GOAL-03:** достоверность и безопасность → явные ограничения → связность поездки → полнота → скорость → красота формулировок.
2. **Звезда (ARCH-01).** Все вызовы инструментов и записи состояния проходят через центральный оркестратор. Компоненты не вызывают друг друга напрямую.
3. **Минимум LLM (ARCH-04).** LLM занимается только естественным языком: разбирает запрос и формулирует объяснение. Факты, цены, наличие и соблюдение условий проверяет код.
4. **Реальные адаптеры с первого среза.** Mock и Live стоят за одним логическим интерфейсом инструментов. Режим всегда виден.
5. **Ничего не выдумывать.** Существенный факт либо подтверждён источником, либо явно помечен как Mock, `unknown` или оценка.

### 2.2. Состав (один сервис, один контейнер, Python 3.12)

### 2.4. Цикл одного хода (ARCH-02)

1. **API.** Проверка входа, блокировка сессии, присвоение `request_id`, сверка `trip_revision`.
2. **Интерпретатор** возвращает `InterpretationDelta`, она проверяется по схеме.
   - Каждый `source_span` должен буквально встречаться в тексте пользователя. Если нет, ограничение отклоняется и становится вопросом или `unparsed`.
   - `InterpretationDelta` — это патч к `TripRequest` из тех же типов §7, а не параллельная схема (DEC-30).
3. **Календарь** разрешает даты: `reference_datetime`, исходная фраза, часовой пояс, правило, статус. Изменения сливаются в черновик `TripRequest`. По `change_set` и таблице REPLAN-01 определяется, что инвалидировать.
4. **Политика уточнений.** Если есть `blocking_now`, задаётся один компактный раунд из 2–3 вопросов, ревизия фиксируется, ответ уходит пользователю. Если блокирующая неопределённость остаётся, допускаются следующие раунды (UC-02).
5. **Домены** формируют `ToolRequest[]` для волны 1: транспорт туда и обратно (DEC-27), отели, геокодинг. Оркестратор применяет политику и лимиты и выполняет независимые чтения параллельно.
6. **Нормализация** в `TravelOffer`, `HotelOffer` и `SourceReference`, проверка недоверенных данных. Затем ядро оценивает ограничения, ранжирует и проверяет, активировалась ли ветка FALLBACK.
7. **Волна 2 для лучших K:** детали отелей, трансфер. Число волн и K задаются конфигурацией (приложение A).
8. **Сборка `TripPlan`:** стыки, итоговая цена и её полнота, актуальность офферов, покрытие условий, `stop_reason`, непроверенные источники.
9. **Composer** формулирует ответ по таблице фактов, затем проверка фактов. При нарушении используется шаблон.
10. **Атомарная запись** новой ревизии. Если ход не удался, последняя согласованная ревизия не меняется.

### 2.10. Транспорт, трансферы и их стоимость (аудит, п. 4)

**Межгород.** Основной источник P0 — Tutu: ж/д и авиа, после утверждения DEC-09. Автобус и мультимодальные маршруты — P1. Резерв — строгий Replay, иначе `unknown` или частичный результат (DEC-23).

**2ГИС.** Остаётся в архитектуре как **отдельный необязательный адаптер** `get_transfer_options` с источником `2gis_public_transport`. Почему не обязательный:
- подтверждены только 3 пары маршрутов в Казани;
- дата, время, расписание и тарифы не проверены, раунд 18 не выполнен;
- покрытие других городов неизвестно;
- нужен собственный лицензированный ключ;
- нужно отдельное утверждение.

Без 2ГИС путь P0 работает: OSRM даёт время, стоимость остаётся `unknown`.

**Политика стоимости трансфера:**

1. **Подтверждённые тарифы.** На 24.10 подтверждённых источников нет. Кандидаты (все НП):
   - тарифы 2ГИС;
   - Tutu `search_etrain` для аэроэкспресса и электричек;
   - официальные тарифы перевозчиков — интеграция только при наличии разрешения, без скрейпинга.
2. **Расчётная оценка.** Допускается только при утверждённом методе (DEC-18). Обязательна маркировка «оценка»: метод, входные данные, дата. Оценка **не входит** в подтверждённую сумму, итог остаётся `partial`.
3. **Неизвестная стоимость.** `price.amount=null`, `total_completeness=unknown` у компонента, указан `unknown_reason`.
4. **Влияние на итог.** Итог поездки — `partial`, показывается «известная часть» с перечнем неизвестных. Бюджет:
   - известная часть уже больше бюджета → `violated` с величиной превышения;
   - иначе → `unknown`.
5. **Демо-покупка.** Трансфер не «покупается». Он показывается в корзине как информационная позиция: «стоимость не подтверждена; оплачивается отдельно». По UC-08 требуется отдельное согласие с перечисленными рисками.
6. **OSRM** даёт только расстояние и время на автомобиле по дорожной сети, без пробок. **Это никогда не стоимость.** Цена из расстояния без метода, утверждённого в DEC-18, не выводится. Можно ли считать оценку OSRM основанием для `matched` на стыке — решение DEC-19.

### 2.11. Источники, доказательства, защита от вымысла

- Каждый существенный факт в TripState ссылается на `SourceReference`: провайдер, инструмент, URL из ответа, `retrieved_at` или `generated_at`, `external_id`, `data_mode`, `verification_status`, `limitations`.
- `verification_status=verified` означает подтверждение конкретным источником, а не объективную истину (CONTRACT-01).
- **Composer** получает таблицу фактов и вставляет их через слоты. В свободном тексте запрещены цифры, суммы, даты и названия, если они не пришли из слотов. При нарушении используется шаблонный ответ (TEST-04).
- Контакты, сайты и телефоны берутся только из полей источника. Нет проверенного контакта — так и пишем (AVAIL-01).
- **Противоречия.** Поиск против деталей или два источника → `verification_status=conflicting`. Показываются оба значения, молча ничего не выбирается.
- Фраза «вариантов нет» допустима только при `ToolResult.status=empty` и завершённом поиске. Форма: «источник X не вернул вариантов по этим параметрам». При остановке по лимиту или ошибке пишем «поиск не завершён» (FALLBACK-01, SEARCH-STOP-01).

### 2.12. Безопасность (SECURITY-01, ARCH-03, ARCH-07)

- **Allowlist «сервер + инструмент» по принципу deny-by-default.** Для `fetch_resource` дополнительно задаётся список URI. Запрет проверяется **в коде до обращения к сети**.
- **Tutu.** Инструмент `register_checkout_passengers` запрещён всегда: он создаёт реальный заказ. `create_checkout_link`, `get_rail_seatmap` и `get_*_instructions` — по DEC-10.
- **Закрепление схем.** При старте и проверке здоровья фиксируется хеш схем разрешённых инструментов. Схема изменилась → инструмент закрывается (`error_code=schema_changed`) и включается деградация.
- **Недоверенные данные.** Тексты ответов и поле `instructions` сервера — данные, а не команды. Проверяются URL (только домены из allowlist провайдера), валюты, координаты, диапазоны, даты, телефоны.
- **Секреты** только из окружения. `.env` исключён из git, `.env.example` содержит одни имена переменных. Исследовательские JSON не импортируются: в них может быть ключ 2ГИС. Тест на секреты входит в CI.
- **Логи** структурированы по `request_id` и `trip_id`, без текстов пользователя, ключей и персональных данных.
- **У LLM нет инструментов и прав на запись.** Ограничены размер входа и частота запросов. CORS — только свой домен. Демо-чек не собирает персональные данные.

### 2.13. Состояние, сессии, идемпотентность (ARCH-05, REPLAN-02)

- SQLite в режиме WAL. Ревизии TripState только добавляются. Таблица `trip_heads` хранит две ссылки: `current_revision` и `last_agreed_revision`.
- Одна сессия обрабатывает один ход за раз. Оптимистичная блокировка по `trip_revision`: несовпадение → 409.
- Подтверждение демо-покупки идемпотентно по `confirmation_id`: повтор возвращает тот же чек. Корзина помнит `trip_revision`. Если зависимости изменились, корзина теряет право подтверждения.
- Неуспешная или отменённая пересборка не меняет `last_agreed_revision`.

## 6. Стратегия тестирования

### 6.1. Уровни

| Уровень | Сеть | Данные | Когда запускается |
|---|---|---|---|
| unit, contract, negative | **запрещена** (сокет блокируется в тестах) | фиксированные структуры | каждый коммит |
| adapter | запрещена | **синтетические** фикстуры в формате ответов провайдера; реальные ответы в git не попадают (DEC-24) | каждый коммит |
| e2e_mock, e2e_replay | запрещена | Mock-генератор; локальный Replay | каждый срез |
| integration (live) | разрешена | реальные вызовы только на чтение с лимитом числа вызовов и времени | только явно (`-m live`), с журналом |
| e2e_live | разрешена | реальные провайдеры и LLM | S2, S3, S4, S6 |
| delivery | по ситуации | Docker во внешней среде, README, секреты, манифесты | S1, S6 |
| ui | — | ручной чек-лист с протоколом (автоматизация — DEC-36) | S1, S4, S6 |

### 6.2. Правила
- Mock и фикстуры **не доказывают**, что Live работает (TEST-02). Протоколы и метрики ведутся отдельно для Live, Replay, Mock и смешанных сценариев.
- Заглушка LLM в режиме `replay` — тестовый дублёр. Качество диалога подтверждается только прогоном на Live-LLM.
- Поля записи по AUDIT-01: `requirement_id / test_id / expected / actual / evidence / status / version / environment / data_mode / tested_at`. Допустимые статусы: `PASS`, `FAIL`, `BLOCKED`, `NOT_RUN`.
- Метрики собираются по METRIC-01. Пороги не выдумываются: они согласуются после первых измерений (OPEN-05).

### 10.2. ACCEPT-02 и ACCEPT-03

- **ACCEPT-02.** Отметка «полностью Live» ставится **отдельно**, только по протоколу `e2e_live`, где все критические компоненты в режиме Live. Mock и Replay подтверждают оркестрацию, диалог и интерфейс, но не актуальность данных.

### 10.3. Готовность к демонстрации (go / no-go)

1. Пункты ACCEPT-01 1–8 — PASS. Пункт 9 — PASS или явно записанный BLOCKED с вашим решением.

4. Есть журнал запуска Docker. README соответствует фактической функциональности.
5. В репозитории и журналах нет секретов (T-DLV-SECRETS-01).
6. Функции P1, которые не успели, перечислены в README как «не реализовано».

### 10.4. Критерий готовности компонента (Definition of Done)

Компонент считается готовым, если:

- его тесты прошли и записаны в протокол;
- контрактный снимок актуален;
- документация описывает фактическое поведение;
- в `decision_log.md` есть запись, если применялось умолчание;
- нет секретов.

Без подтверждения работоспособности компонент **не считается готовым**.

## Приложение D. Демонстрационный сценарий (черновик)

1. «Хочу съездить из Москвы в Казань на выходные 20–22 ноября вдвоём, бюджет до 40 000 ₽, лучше поездом, отель с завтраком».
   - Интерпретация показана с фрагментами-основаниями.
   - Уточнение задаётся, только если оно блокирует следующий шаг.
2. Live-поиск с прогрессом. Карточки поездов и отелей со значками Live, источником и «актуально на».
3. План:
   - цена за двоих за весь период;
   - трансфер «время по оценке OSRM, стоимость не подтверждена» → итог `partial`;
   - стыки «прибытие → заезд» со статусами и буферами.
4. Корзина → два согласия (покупка; продолжение при неизвестной стоимости трансфера) → демо-чек. Повторное подтверждение даёт тот же чек.
5. «Едем с собакой» → пересборка. Правила отеля и поезда перепроверены, корзина пересчитана, остальные условия сохранены.
6. «Сдвинь на неделю» → новая ревизия. Старая корзина не подтверждается.
7. Запрос без направления → 3 кандидата из мини-каталога с климатической нормой и пометкой «стоимость требует дат».
8. Имитация сбоя Tutu → частичный ответ или строгий Replay с пометкой «цена на дату, не текущая», без подмены.
